Q1. ESSAY, 3 MARKS. Replaces "differences".

  STATUS: WRITTEN.  In the bank as `lox workarounds <essay>` in the Exam
  venue of 3_lox.md.  Week 3 builds and renders clean.  The 2025 question
  and answer are untouched under Past Exams as `differences 2025`.

  Question:
    Pick one thing that Lox, as described in the book "Crafting
    Interpreters", cannot express, and which you would want in a program
    you were writing for fun.  Describe two different Lox workarounds for
    it.

    For each workaround, explain what it costs.  Then say which of the two
    you would rather write yourself, and why.  There is no single right
    answer here, so make sure your reasons are the kind you could defend
    to the other person in the group.

  Model answer (in the bank) uses `switch` as the missing feature, with
  two workarounds:
      1. An if/else chain dispatching on the operator character.
      2. A table of function values, with a small `apply` function that
         dispatches.  The if chain has not gone away, it has moved.
  The costs are compared honestly, then the answer picks the chain for a
  four-operator calculator and the table for a fifty-command turtle
  program, on the grounds that the turning point is not the number of
  cases but whether the case list changes often.

  Marking scheme, 1 mark each:
      - A real gap in Lox plus a first workaround that would actually work.
      - A second, genuinely different workaround, with its cost stated
        rather than assumed to be free.
      - A choice between the two that is argued rather than asserted.

  Other things students will reach for, all of which have two distinct
  workarounds available: no arrays, no classes, no modulo, no string
  methods, no `do...while`.

  Note on the shape of the question.  This is deliberately not a "describe
  two differences between Java and Lox" question, because the 2025 paper
  already had one and students can pattern-match the structure.  Asking
  for a design decision and a defended preference gets at the same
  "understand some basic Lox design decisions" goal without repeating the
  form.  Java is not mentioned at all, so if the paper needs to keep
  testing the Java contrast, that has to come from elsewhere.


Q8. GIFT, 1 MARK. Replaces "Representing Unary".
  STATUS: WRITTEN.  In the bank as `tree shape for a unary node <gift>` in
  the Exam venue of 5_representing.md.  Week 5 builds and renders clean,

  Question:
    In the Lox interpreter from "Crafting Interpreters", the unary
    expression `-a` is parsed into a node of class `Expr.Unary`, which
    the code generator declares with a `Token operator` field and a
    single `Expr right` field.  Which of the following trees is
    correct?{
      = A `Unary` node whose `operator` field holds the `-` token, with a
        single child representing "a" in its `right` field.
      ~ A `Unary` node with two children, both representing "a".
      ~ A `Grouping` node wrapping the `-` token, with a child
        representing "a" beneath it.
      ~ A single `Literal` node whose value is the string "-a", with no
        children.
    }

  What the NB changed.  Naming the class turns 2025's two arity
  mistakes into four separate errors, so each option is a different
  wrong idea:
    - wrong field count, right class (a `Unary` with two children)
    - wrong class by reaching for `Grouping`
    - flattening, where the operator is swallowed into a `Literal` value
    - and the correct answer, which names both declared fields
  The 2025 distractor is kept in the same slot, so a student who
  pattern-matches to it still picks the same wrong answer.

  Two costs of naming the class, both accepted.  A student who has read
  the declaration can rule out the two-children option on sight, so the
  arity distractor is weak for anyone who has memorised
  `Unary : Token operator, Expr right`.  It is one mark and the field
  layout is the thing being tested, so that is the right trade.

  The larger cost is the forward reference.  Week 5 never names the node
  classes in its teaching content, so the stem quotes material a student
  meets in week 6, where 6_parser.md:167 shows the declaration this
  question is built on.  Fine for a cumulative paper, and the slot has
  to live where `Representing Unary` sat, but worth remembering that
  this question is really a week 6 question in a week 5 slot.

  Note: this also cleans up two artefacts from the PDF extraction in the
  2025 wording, which read `Abstract Syntax Tree"` and
  `Interpreters""` with stray double quotes.

  Title note: the plan first called this "tree shape for -a".  The
  hyphen has to go because tooling/v2.py:229 cleans item names with
  `[^a-zA-Z0-9_ ]`, and the first build rendered the section as
  "tree shape for a".  Harmless, but a title that silently drops a
  character is not worth keeping.

Q15. GIFT, 1 MARK. Replaces "variable uses".

NB: Approved, put this one in

  STATUS: WRITTEN.  In the bank as `uses in a function body <gift>` in
  the Exam venue of 8_statements_one.md:262.  Week 8 builds and renders
  clean, 1 page, zero LaTeX errors.  The braces print as real braces,
  confirmed by extracting the text back out of the built PDF.

  In the following code, which lines contain a variable _use_.  Don't
  include variable _declarations_ in your answer

  \ttfamily
  var x = 1;\
  fun f(a)\{\
  \vrule width 0pt height 0pt depth 0pt\kern1em return a + 1;\
  \}\
  print f(x);
  \rmfamily
  {
    ~1 only
    ~2 and 3
    ~3 only
    =3 and 5
    ~2, 3, and 5
    ~none
  }

  Note: five lines.  Line 1 declares x.  Line 2 declares f and a, and
  nothing else, because the opening brace is on that line.  Line 3 uses
  a.  Line 4 is the closing brace, so it is neither a declaration nor a
  use.  Line 5 uses f and x.  Answer is 3 and 5.

  Splitting `fun f(a){` from `return a + 1;` is the whole point, and it
  was your fix.  The original had `fun f(a){ return a + 1; }` on a
  single line, so that one line both declared the parameter a and used
  it in `a + 1`, and the marked answer of `3 only` was wrong.  With the
  body on its own line, no line both declares and uses, so "which lines
  contain a use" has exactly one right answer.

  Option set is shaped like the RAT original it replaces, at
  8_statements_one.md:59, which is also six options.  `2 and 3` catches
  students who count the parameter list as a use, `2, 3, and 5` catches
  those who count every declaration line, and `3 only` catches those who
  forget the print.  `4 only` and `4 and 5` are unavailable as options,
  since line 4 is the brace, which is why there are two `only` traps
  rather than three.

  I also deliberately avoided assignment targets like `x = y;` because
  the bank is inconsistent about them. `landr` treats a write as "both",
  while `variable uses` treats it as a use.  Leaving them out keeps that
  separate ambiguity out of the question.

  FORMATTING, the fiddly part.  A literal `{` cannot go in a GIFT stem.
  The answer block is split off with `re.split(r"(?<!\\){", item_data)`
  at tooling/v2.py:247, which needs exactly one unescaped `{` in the
  whole item and the answer block already claims it.  The unescaped
  version fails the build outright:

      File "tooling/v2.py", line 247, in <module>
        question, rest = re.split(r"(?<!\\){", item_data)
      ValueError: too many values to unpack (expected 2)

  So the braces have to be written `\{` and `\}`, and the question is
  whether the student then sees the backslashes.  They do not, but only
  because this is NOT written inside a code fence.  Two things follow
  from that, both learned by getting it wrong first.

  Inside a fence, braces stay literal, because a fenced block becomes
  `verbatim` and `verbatim` does not process escapes.  So
  `fun f(a)\{` inside a fence prints as `fun f(a)\{`, backslash and all,
  which reads as if Lox needs escaping.  Worse than useless in exam
  content.  This is why there is no fence here at all.

  With no fence the `\{` is ordinary LaTeX, and `\{` is precisely how
  you write a literal brace, so it prints as `{`.  A trailing `\` on
  each line is a pandoc hard line break, which becomes `\\`.  Verified
  output from the build:

      \ttfamily
      var x = 1;\\
      fun f(a)\{\\
      \vrule width 0pt height 0pt depth 0pt\kern1em return a + 1;\\
      \}\\
      print f(x); \rmfamily

  And the PDF text, read back out of the built Exam.pdf:

      var x = 1;
      fun f(a){
      return a + 1;
      }
      print f(x);

  `\ttfamily` and `\rmfamily` are used because `\texttt{...}` would need
  a brace pair, which we cannot spare.  They take no arguments, so they
  cost nothing, and `\rmfamily` puts the option list back in roman.
  Two trailing spaces work as the line break too, if the trailing
  backslashes read as too cryptic in the source.

  THE INDENT, and this is the part that cost the most time, because the
  obvious answer is wrong.  Indent is
  `\vrule width 0pt height 0pt depth 0pt\kern1em `.

  The obvious answer is `\quad`.  It compiles cleanly, and it is
  silently discarded.  I shipped it, believed it worked because latexmk
  exited 0, and it was a no-op.  The reason is that `\quad` is
  *discardable* glue, and TeX throws away discardable material at the
  start of a line, which is exactly where it lands, immediately after a
  `\\`.  Same for `\qquad`, `\enspace`, `\ ` and a bare `\kern`.

  Caught it by measuring x positions in the built PDF rather than by
  eyeballing the render or trusting the exit code.  Line starts:

      x=76.71  L0 noindent
      x=61.77  L1 \quad            <- same as no indent
      x=61.77  L2 \qquad           <- same
      x=61.77  L3 \enspace         <- same
      x=61.77  L4 backslash-space  <- same
      x=91.66  L5 \hspace*{30pt}   <- moved
      x=61.77  L6 noindent         <- back to baseline

  Compiled clean with zero errors, indented nothing.  The lesson for
  the rest of the bank: a clean latexmk exit proves the code COMPILES,
  it proves nothing about what it RENDERS.  Measure the output.

  `\hspace*` is the starred form precisely because it defeats this
  discard, by starting the line with a non-discardable rule.  But
  `\hspace*{1em}` needs a brace pair, which is the one thing we cannot
  spend.  So the indent is spelled out as its two parts: a zero-size
  `\vrule` to anchor the line, then `\kern1em` for the width.  Both are
  brace-free, and the two together match `\hspace*{1em}` exactly:

      x=71.73  \vrule ... \kern1em
      x=71.73  \hspace*{1em}

  One more trap on the way: `\kern1em` must not be run straight into the
  next word.  TeX reads a control word as the longest run of letters, so
  `\kern1emreturn` would be fine but `\quadreturn` asks for a command
  called `quadreturn` and fails to compile:

      Undefined control sequence   # \quadreturn a + 1;

  The space in `\kern1em return` is therefore load-bearing.

  The price of this route is that the code is not verbatim, so anything
  that is a LaTeX or markdown metacharacter needs escaping.  Braces,
  `#`, `%`, `&`, `_` and `$` all need care.  This snippet has none of
  those beyond the braces, so it is safe here, but it is a sharp tool
  for arbitrary code.

Q16. ESSAY, 3 MARKS. Replaces "strange".

NB: this is the same question - the variation needs to be more. . If you can come up with a MC question instead of an essay - even better!
  question: |
    Write some lox code which shows one of the "strange" or "interesting"
    things you can do because assignment is an expression in our parser.
    What is the output expected of this code?

  answer: |
    ```
    var a;
    var b;
    var c;
    a = b = c = 5;
    print a + b + c;
    ```
    This prints 15.

    Assignment is an expression in Lox, so it has a value (whatever was
    just assigned) and it can appear anywhere an expression can appear,
    including on the right of another assignment.  So `a = b = c = 5` is
    not a syntax error, it is three nested assignment expressions.  The
    innermost `c = 5` evaluates to 5, then `b = (c = 5)` assigns 5 to b
    and evaluates to 5, then `a = (b = (c = 5))` assigns 5 to a.  All
    three hold 5, so the sum is 15.

    In Java none of this would compile.  `a = b = c = 5;` is an error
    because in Java an assignment is a statement, not an expression, so
    it has no value to hand to the assignment on its left.  Same rule
    that makes the classic `while (x = x - 1)` loop compile in C but not
    in Java.

  Note: the 2025 version used `while (x = x - 1)`. This one uses chained
  assignment, so it tests the same idea by a different route.

Q23. GIFT, 2 MARKS. Replaces "which needs lexical scoping".

  Only one of the following programs would have an error if we had not
  fixed the name resolution to account for lexical scopes.  Which one?{
    ~```
    var a = 5;
    {
        fun foo(a) {
            return a + a;
        }
        print(foo(1));
        var b = 2;
        print(foo(3));
    }```
    ~```
    var a = 5;
    {
        fun foo() {
            return a + a;
        }
        print(foo());
        var b = 2;
        print(foo());
    }```
    ~```
    var a = 5;
    {
        var a = 2;
        fun foo() {
            return a + a;
        }
        print(foo());
    }```
    =```
    var a = 5;
    {
        fun foo() {
            return a + a;
        }
        print(foo());
        var a = 2;
        print(foo());
    }```
  }

  Correct answer is the fourth program.  `foo` is called before the
  block's `var a = 2;` runs, but the declaration is hoisted into the
  block's own environment, so reading `a` there finds an uninitialised
  binding.  Without lexical scoping `a` would resolve to the global 5
  and the program would quietly print 10 instead of erroring.
