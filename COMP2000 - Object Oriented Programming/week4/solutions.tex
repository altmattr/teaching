\section*{Self Study Exercises}

\subsection*{Exercise 1: Inheritance hierarchy}

\begin{lstlisting}
class Animal {
    String name;

    Animal(String name) { this.name = name; }
    void makeSound() { System.out.println("Some sound"); }
}

class Mammal extends Animal {
    double bodyTemp;

    Mammal(String name, double bodyTemp) {
        super(name);
        this.bodyTemp = bodyTemp;
    }
}

class Dog extends Mammal {
    Dog(String name, double bodyTemp) {
        super(name, bodyTemp);
    }

    @Override
    void makeSound() { System.out.println("Woof!"); }

    public static void main(String[] args) {
        Dog d = new Dog("Rex", 38.6);
        d.makeSound();   // Woof!
    }
}
\end{lstlisting}

\texttt{Dog} inherits \texttt{name} from \texttt{Animal} (via \texttt{Mammal}), \texttt{makeSound()} from \texttt{Animal} (which it then overrides), and \texttt{bodyTemp} from \texttt{Mammal}.

\subsection*{Exercise 2: Method overriding and polymorphism}

\begin{lstlisting}
abstract class Shape {
    abstract String areaFormula();
}

class Circle extends Shape {
    @Override
    String areaFormula() { return "Area = Pi x r^2"; }
}

class Rectangle extends Shape {
    @Override
    String areaFormula() { return "Area = s1 x s2"; }
}

public static void main(String[] args) {
    Shape[] shapes = { new Circle(), new Rectangle() };
    for (Shape s : shapes) {
        System.out.println(s.areaFormula());
    }
}
\end{lstlisting}

\textbf{Late binding (dynamic dispatch)} ensures the correct overridden method is called based on the object's runtime type, not the reference type. The JVM looks up the method in the actual class of the object at runtime.

\subsection*{Exercise 3: Interface fundamentals}

\begin{lstlisting}
interface Playable {
    void play();
}

class Guitar implements Playable {
    @Override
    public void play() { System.out.println("Strumming strings..."); }
}

class Chess implements Playable {
    @Override
    public void play() { System.out.println("Moving pieces..."); }
}

public static void main(String[] args) {
    List<Playable> items = new ArrayList<>();
    items.add(new Guitar());
    items.add(new Chess());
    for (Playable p : items) {
        p.play();
    }
}
\end{lstlisting}

\texttt{extends} is used between classes to inherit fields and methods (implementation inheritance).  \texttt{implements} is used between a class and an interface to fulfil a contract (type inheritance only).  A class can extend only one class but implement many interfaces.

\subsection*{Exercise 4: Multiple interfaces}

\begin{lstlisting}
interface Flyable { void fly(); }
interface Swimmable { void swim(); }

class Duck implements Flyable, Swimmable {
    @Override
    public void fly() { System.out.println("Flying..."); }
    @Override
    public void swim() { System.out.println("Swimming..."); }
}

public static void main(String[] args) {
    Duck d = new Duck();
    Flyable f = d;    // Duck treated as Flyable
    Swimmable s = d;  // Duck treated as Swimmable
    f.fly();
    s.swim();
}
\end{lstlisting}

Multiple interface implementation lets a single class participate in multiple type contracts, enabling flexible designs where objects can be used polymorphically through different interfaces.

\subsection*{Exercise 5: Default methods}

\begin{lstlisting}
interface Playable {
    void play();
    default void describe() {
        System.out.println("This is a playable thing.");
    }
}

class Guitar implements Playable {
    @Override
    public void play() { System.out.println("Strumming..."); }
    @Override
    public void describe() { System.out.println("A musical instrument."); }
}

class Chess implements Playable {
    @Override
    public void play() { System.out.println("Moving pieces..."); }
    // describe() inherited as-is from the interface
}
\end{lstlisting}

Output for \texttt{Guitar}: \texttt{"A musical instrument."} \\
Output for \texttt{Chess}: \texttt{"This is a playable thing."}

Classes are not required to override default methods.  If they do, the override takes precedence.

\subsection*{Exercise 6: Valid declarations and safe casts}

\begin{enumerate}
    \item \texttt{A x = new B();} --- \textbf{Valid}. \texttt{B} is a subclass of \texttt{A}, so upcasting is always safe.
    \item \texttt{B x = new A();} --- \textbf{Invalid / compile error}. \texttt{A} is the superclass; a superclass reference cannot be assigned to a subclass variable without an explicit cast (and even then it would throw \texttt{ClassCastException} at runtime).
    \item \texttt{D x = new C();} --- \textbf{Invalid}. \texttt{C} is not a subclass of \texttt{D} (it is the superclass of \texttt{D}), so this assignment fails.
    \item \texttt{A x = new D();} --- \textbf{Valid} (upcast).  \texttt{(C) x;} --- \textbf{Safe}, because \texttt{D} \texttt{extends} \texttt{C}, so the object's runtime type (\texttt{D}) is a \texttt{C}.  This cast will never throw \texttt{ClassCastException}.
\end{enumerate}

\subsection*{Exercise 7: Overloading vs overriding}

\begin{itemize}
    \item \textbf{Pair 1: Overloading.} Same method name, different parameter types (\texttt{int} vs \texttt{double}).  Both methods live in the same class.
    \item \textbf{Pair 2: Overriding.} Both methods have identical signatures (\texttt{speak()}) and are in a subclass-superclass relationship.  The subclass version replaces the parent version when called on a \texttt{Child} reference.
    \item \textbf{Pair 3: Overloading.} Same method name, different number of parameters (two vs one).  Both in the same class.
\end{itemize}

Key distinction: overloading is about \textbf{different parameter lists} within the same class (compile-time); overriding is about \textbf{replacing behaviour} in a subclass (run-time).

\subsection*{Exercise 9: Reference vs value semantics}

Output:
\begin{verbatim}
5
hello world
\end{verbatim}

\texttt{int} is a \textbf{primitive type}.  When we write \texttt{int b = a;}, the value \texttt{5} is copied into \texttt{b}.  Changing \texttt{b} to \texttt{10} does not affect \texttt{a}.  Primitives are stored directly in the variable.

\texttt{StringBuilder} is a \textbf{reference type}.  \texttt{sb2 = sb1} copies the \emph{reference} (memory address), not the object itself.  Both \texttt{sb1} and \texttt{sb2} refer to the same object in memory.  Calling \texttt{sb2.append(" world")} mutates that shared object, so reading \texttt{sb1} reflects the change.

\subsection*{Exercise 10: Partial interface implementation and abstract classes}

\begin{lstlisting}
interface Repairable {
    void repair();
    void inspect();
}

abstract class Vehicle implements Repairable {
    // Only implements repair(), not inspect()
    @Override
    public void repair() { System.out.println("Fixing vehicle..."); }
    // inspect() is left unimplemented -> class must be abstract
}

class Car extends Vehicle {
    @Override
    public void inspect() { System.out.println("Inspecting car..."); }
}
\end{lstlisting}

If a concrete class (\texttt{Vehicle}) claims to implement an interface but does not provide bodies for all methods, the compiler would reject it.  Declaring the class \texttt{abstract} defers the obligation: subclasses (\texttt{Car}) must complete the implementation or themselves be declared abstract.  The \texttt{abstract} keyword signals that the class is intentionally incomplete and cannot be instantiated directly.
